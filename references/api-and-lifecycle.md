# 专题：API、状态机与资源回收

[统一课程](../README.md) · [面试题与答案](../expert-assessment/by-module/README.md)

这是按主题组织的阅读与实验资料；课程模块及考核以总目录为准。


前置：能手动启动 microVM。目标：把手工步骤组织成能够重试、检查和清理的管理流程。

## 1. 先学基础

**Unix domain socket。**它是同一宿主机进程间通信的接口，可以承载 HTTP。Firecracker API 使用 Unix socket；URL 中的 `localhost` 不表示你已经公开了一个 TCP 端口。socket 及其目录权限属于管理面的访问控制。

**状态机。**一个操作是否允许取决于当前状态。启动前配置资源、启动后进行受支持的运行时操作，不能假定所有配置都能随时改。具体允许项查对应版本 API，不凭 HTTP 方法推断。

**幂等与结果不确定。**请求超时可能表示未执行，也可能表示已执行但响应丢失。管理层必须通过稳定任务 ID、状态查询与资源核对决定下一步。不能假定重复发送任何 Firecracker API 都有相同效果。

**补偿与对账。**创建 VM 会产生目录、socket、进程、磁盘和网络资源，中途失败需要回收。对账是持续比较期望状态与实际状态，并修复差异；它也处理管理进程崩溃后留下的资源。

## 3. 管理层状态机

可以给自己的执行器设计：`Requested → Preparing → Booting → Ready → Running → Stopping → Cleaning → Finished`。任一步骤失败进入 `Cleaning`，待清理结束再标记失败终态；无法完成清理的对象保持可重试状态。

**这些是课程设计的管理层状态，不是 Firecracker API 的原生状态枚举。**运行期暂停是一个额外分支，需要同时处理任务超时、计费或租约计时的语义。

每个实例记录：实例 ID、任务 ID、版本、资源清单、期望状态、观察状态、进程身份与更新时间。仅保存 PID 不足以安全地恢复管理，因为 PID 可能被复用。

## 4. 实验：实现或伪代码演练一个管理器

1. 把镜像与启动模块步骤拆成 `prepare/start/wait_ready/stop/cleanup`；每步列出输入、成功依据和失败补偿。
2. 在 Linux 上连续完成 3 次创建与清理，记录每轮唯一 ID 和资源清单。
3. 在准备好目录、尚未启动 VM 时模拟失败，验证清理能执行两次而不误删其他实例。
4. 在自己的测试 VM 运行后，停止其管理脚本；重新启动管理脚本，尝试找回已存在的实例，不重复创建。
5. 模拟一次“操作成功但调用方没收到响应”，先查询与核对，再决定重试或结束。

源码与脚本可以只保留在各自实验环境。本课重点是操作语义，不要求实现多机控制面。关机区分客户机配合的正常结束与管理层超时后的进程终止；具体机制要适配客户机、架构和所选版本。

## 5. 验收

画状态图，列出至少 3 个故障注入点。结束时检查实例进程、socket、实验磁盘引用和本课创建的其他资源。清理失败要留下可重试记录，不能只把数据库状态改成“已删除”。
