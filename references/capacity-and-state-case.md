# 参考案例：多租户短任务执行平台

[统一课程](../README.md) · [面试题与答案](../expert-assessment/by-module/README.md)

这是按主题组织的阅读与实验资料；课程模块及考核以总目录为准。


本案例用于容量计算与状态设计阅读。考核题目、答案与评分请从上方“面试题与答案”入口进入。

## 一、场景与设计约束

你负责设计一个基于 Firecracker 的服务。用户提交 Linux 用户态任务，平台在隔离环境中运行，返回退出码与有限大小的输出。当前只有一台 Linux 实验服务器，产品设计需能扩展为多节点集群。

以下数字是**假设条件，用于容量计算，不是 Firecracker 性能承诺**：

| 条件 | 给定值 |
| --- | --- |
| 用户 | 100 个租户，任务彼此不可信 |
| 常态流量 | 40 个任务/秒 |
| 突发流量 | 200 个任务/秒，持续 30 秒 |
| 平均任务执行时间 | 5 秒，不含排队和准备 |
| 平均 CPU 消耗 | 每任务总计 0.5 CPU 核秒 |
| 每任务客户机内存 | 256 MiB |
| 每任务总内存预算 | 暂按 320 MiB，包含客户机与宿主侧预算，之后必须实测 |
| 节点规格 | 16 核、64 GiB；内存预留 8 GiB，CPU 目标利用率不超过 70% |
| 任务限制 | 最长执行 60 秒，输出最多 1 MiB |
| 就绪目标 | 对接纳的任务，从 API 接收到 sandbox 可接收任务的 P95 小于 1 秒，包含排队 |
| 任务语义 | 可能访问外部系统，默认不能假定重试无副作用 |

阅读时沿以下维度分析：

1. 澄清需求、信任边界与失败语义。
2. 给出容量估算和瓶颈判断，说明如何处理突发流量。
3. 画出组件、数据流和管理流。
4. 定义任务、执行尝试、VM 的身份与状态。
5. 说明镜像、磁盘、网络、jailer 与资源配额如何配置和管理。
6. 比较冷启动、预启动实例池和快照恢复的使用条件。
7. 处理超时、重复消息、节点失联和结果提交失败。
8. 给出验证方法、观测指标和上线前仍需确认的问题。

你可以明确拒绝暂时无法满足的延迟目标，但必须指出证据需求和替代策略。不要用“Firecracker 很快”替代应用就绪与排队分析。

## 二、分析检查点

先写下判断，再对照后面的案例分析。

| 检查点 | 分析重点 |
| --- | --- |
| 1. `/actions` 启动成功，为什么不能立即把用户请求发进 VM？ | 就绪层次 |
| 2. 有 KVM 隔离，为什么仍需要 jailer、网络策略与输出上限？ | 分层隔离与资源通道 |
| 3. 从一个快照克隆 100 台，哪些信息必须重新处理？ | 身份、随机状态、连接与磁盘 |
| 4. 调度器写了“运行中”后崩溃，但 VM 是否启动未知，怎么办？ | 意图与实际状态、对账 |
| 5. 节点失联，旧任务实际上仍运行，怎么避免两个尝试一起提交结果？ | 租约、代次与 fencing |
| 6. 客户机执行完成，但结果回传断开，重跑还是报错？ | 不确定结果与业务副作用 |
| 7. API 恢复只用了很短时间，首个请求仍很慢，查哪里？ | 按需加载、缺页与应用状态 |
| 8. 队列越来越长，但总 CPU 只有 40%，为什么？ | I/O、单线程、配额与调度瓶颈 |
| 9. 用户要求任意任务绝不重复执行，你能直接承诺吗？ | 分布式失败与可实现语义 |
| 10. 客户机退出后，哪些资源可能仍留在宿主机？ | 清理所有权与孤儿资源 |
| 11. 跨 CPU 型号与宿主内核恢复快照，如何控制兼容性？ | CPU 模板、版本矩阵与验证 |
| 12. 给设备后端加工作线程池，会怎样影响暂停和快照？ | 在途操作、状态一致性 |

## 三、案例分析

<details>
<summary>参考 1：需求澄清与边界</summary>

询问任务允许的架构、依赖、网络访问、持久数据、最大并发和优先级；询问平均时间之外的分布，尤其长任务比例。确认失败任务是否允许重试，哪些操作可能写外部数据库或调用收费接口。

明确 P95 的起止点、统计窗口、接纳与拒绝策略，不能靠丢弃慢样本达标。分别报告就绪、任务完成和结果可查询延迟，以及拒绝率、失败率与队列等待。

把客户机和任务输入视为不可信，把节点管理器、Firecracker API socket、镜像来源和状态存储放入受保护管理边界。可信镜像准备与不可信任务执行分离；不让租户直接操作宿主高权限资源。

</details>

<details>
<summary>参考 2：容量计算</summary>

在稳定流量与给定平均值成立的假设下：

- 常态平均执行并发：`40 × 5 = 200`。
- 常态内存预算：`200 × 320 MiB = 62.5 GiB`。
- 常态 CPU 需求：`40 × 0.5 核秒/秒 = 20 核`。
- 每节点可规划内存：`64 − 8 = 56 GiB`。
- 每节点 CPU 预算：`16 × 70% = 11.2 核`。
- 常态节点下界：内存 `ceil(62.5/56)=2`，CPU `ceil(20/11.2)=2`，初步取 2。

持续 30 秒的突发长于平均执行时间，可以用 200/s 做一个稳态近似：

- 执行并发约 `200 × 5 = 1000`。
- 内存预算约 `312.5 GiB`，需至少 `ceil(312.5/56)=6` 个节点。
- CPU 需求约 `100 核`，需至少 `ceil(100/11.2)=9` 个节点。
- 因而 CPU 给出更强的初步下界：9 个节点。

这些结果没有计入启动/清理 CPU、预热池、分布尾部、节点间不均衡、磁盘/网络和额外控制面成本。2 与 9 是计算下界，不是部署建议。简化同规格模型下，常态承受一节点损失至少需要 3 节点；若要求突发期间也承受同样损失，下界为 10，仍需验证剩余瓶颈。

只有两台节点不能在不排队或拒绝的情况下直接承载全部突发。若扩容准备时间长于就绪 SLO，就要预留可用容量、预热资源，或明确限流、排队上限和降级合同。运行着的预热 VM 消耗内存；只缓存快照文件并不等于已经准备好足够执行容量。

</details>

<details>
<summary>参考 3：组件与数据模型</summary>

合理方案包含：鉴权与配额入口、持久任务状态、有界队列、调度器、节点管理器、镜像/快照缓存、jailer + Firecracker、客户机 agent、结果与有限日志存储、清理和对账器。

任务 ID 表示业务请求，attempt ID 表示一次执行，instance ID 表示 VM 资源。每次尝试记录节点、执行代次、租约、镜像、超时和资源需求。结果按任务/尝试绑定，提交时验证当前合法代次。

调度先筛架构、兼容条件、可用容量和租户配额，再考虑缓存命中、负载与公平性。数据库与队列的双写使用 outbox 或等价恢复机制。单机原型可以合并组件，但保持这些职责和状态语义。

</details>

<details>
<summary>参考 4：生命周期、结果与失败</summary>

持久化提交意图与幂等键 → 入队 → 获取执行权并预留容量 → 准备磁盘/网络 → 启动或恢复 → 客户机与应用就绪 → 执行任务 → 持久化结果 → 提交完成状态 → 清理资源。

每一步都有超时、可识别副作用和恢复依据。Firecracker 启动成功只是其中一个节点。任务最长执行 60 秒还需要单独定义准备、排队与清理的超时。

节点失联后，先把状态标为不确定。新尝试获得更高执行代次，结果存储拒绝旧代次提交。节点侧租约失效可触发停止任务，但网络分区下不能只依赖这一点保证外部副作用唯一。外部操作要有业务幂等键或支持 fencing；无法做到时，暴露“不确定结果”并按用户合同处理。

结果提交与清理分开重试：已持久化成功结果不因后续删除 TAP 失败而变成执行失败。删除操作按资源所有权和实例身份核对，避免 PID 复用或共享镜像导致误删。

</details>

<details>
<summary>参考 5：网络、存储、隔离与快照</summary>

任务控制可使用受限的 guest agent 协议，经 vsock 或私有网络与宿主通信。客户机互联网流量通过明确的 TAP、路由与策略出站；按租户规则允许目标，不把 NAT 当成安全策略。

基础镜像不可变，任务具有独立可写空间，持久盘另有生命周期。使用 jailer 或等效约束、合适的 UID/GID、cgroup、默认 seccomp 与宿主网络策略。落实 CPU、内存、磁盘/网络速率、任务时长和输出上限。1 MiB 达到上限后的行为必须明确：截断并标记、继续丢弃，或终止任务，不能静默改变结果。

快照只保留通用初始化状态。磁盘与外部资源由平台配套管理；恢复后处理身份、凭证、用户态随机状态和连接，再进行应用就绪检查。维护版本和硬件兼容矩阵，必要时冷启动回退。快照内存与模板文件有访问控制、校验和运行期引用管理。

冷启动、预启动池、快照恢复不是单纯谁更快：分别比较常驻内存、模板维护、缓存未命中、恢复 I/O、客户机唯一性和应用兼容成本。

</details>

<details>
<summary>参考 6：验证与可观测性</summary>

跟踪排队、镜像准备、启动/恢复、agent 就绪、应用就绪、执行、结果提交和清理阶段。观测宿主 CPU/内存/cgroup、磁盘与网络压力，以及 API 和设备错误。关联 task/attempt/instance ID，并限制日志体积和指标标签基数。

分别压测冷启动、文件缓存命中/未命中的快照恢复、并发启动和稳态执行；报告环境、负载分布、成功数、失败数、分位数与样本量。测试节点管理器重启、结果确认丢失、磁盘满、任务超时和输出超限。

SLO 是需要实测满足的目标，尤其包含排队时，不能用官方微基准替代端到端证明。单台 Linux 可验证基本路径与部分故障，但多节点分区和故障接管仍需独立验证。

</details>
