# 专题：内核、rootfs 与第一次启动

[统一课程](../README.md) · [面试题与答案](../expert-assessment/by-module/README.md)

这是按主题组织的阅读与实验资料；课程模块及考核以总目录为准。


前置：运行时基础模块环境检查通过，能够使用 Linux shell。目标：启动一台 microVM，并按阶段解释失败原因。

## 1. 先学基础

**内核与用户空间。**Linux 内核负责内存、进程、文件系统和驱动；shell、Python、服务程序属于用户空间。Firecracker 二进制运行在宿主机，客户机内核镜像运行在 microVM，两者不是同一个文件。

**rootfs。**根文件系统提供客户机的 `/`，包含用户态程序、动态链接库、配置和启动程序。一个 ext4 镜像可以作为宿主机上的普通文件保存，并通过虚拟块设备呈现给客户机。OCI 容器镜像包含层与元数据，不能直接当作 ext4 块设备镜像使用；导出文件后构建 rootfs 还需处理启动程序、依赖与权限。

**PID 1 与启动参数。**内核就绪后需要启动第一个用户态进程。根设备、串口控制台和 init 路径等参数决定系统如何继续启动。不同架构、镜像布局和设备配置可能要求不同参数，照搬另一套镜像的参数容易失败。

**启动就绪的三层含义。**Firecracker 进程存在、客户机内核运行、应用能处理请求，是三个不同检查点。API 返回启动成功不能代替应用健康检查。

## 3. 启动链路

管理程序准备资源 → 启动 Firecracker 并等待 API socket → 配置内存与 vCPU → 指定内核和启动参数 → 配置 rootfs → 发送 `InstanceStart` → 客户机内核初始化 → 挂载根文件系统 → 启动 PID 1 → 应用就绪。

这是手动 API 路径。配置文件启动是另一种入口，学习时先把手动路径走通，便于知道每一步失败在哪里。

## 4. 实验：最小启动与两个故障

1. 在 Linux 实验位置按选定版本的官方入门准备同架构的 Firecracker、客户机内核和 rootfs；记录版本、来源和文件校验值。资源在实验环境准备，不从 Mac 上传课程文件。
2. 为本次实验建立独立目录与唯一 socket 路径。使用单 vCPU、小内存配置，内存大小以镜像能够正常启动为准。
3. 先使用可信示例镜像完成无额外网络配置的启动，通过串口确认客户机进入用户空间。保存 API 响应、宿主进程日志与串口输出；示例镜像仅用于实验。
4. 在客户机运行 `uname -a`、`cat /proc/meminfo`、`mount`，对照宿主机结果。
5. 新开一轮实验，把内核文件路径改成不存在的路径，观察在 API 配置阶段还是启动阶段失败。
6. 再开一轮，把根设备参数改错，观察是否出现内核输出以及挂载失败信息。恢复正确配置，确认能够再次启动。

故障只修改实验副本或本轮参数。结束后核实对应进程已退出，再清理本次实验资源。不要同时修改内核、rootfs 和启动参数，否则难以判断因果。

## 5. 验收

交付一张启动时间线，明确“API 可用”“客户机用户空间可用”“应用就绪”的观察依据。对两个故障分别记录：现象、证据、失败层、修复方法。能够解释为什么文件存在仍可能启动失败，例如架构、格式、权限或驱动不匹配。
