# 专题：快照、恢复与克隆

[统一课程](../README.md) · [面试题与答案](../expert-assessment/by-module/README.md)

这是按主题组织的阅读与实验资料；课程模块及考核以总目录为准。


前置：完成生命周期、网络、存储课程。目标：定义一个可恢复的完整检查点，并解释克隆后的状态风险。

## 1. 先学基础

**快照与冷启动。**冷启动从内核、根文件系统重新初始化；快照恢复接续先前保存的执行状态。节省初始化工作可能降低启动等待，但保存、存储、加载和首次访问内存也有成本。

**一致性。**内存、CPU/设备状态、磁盘与外部系统若属于不同时间点，恢复后可能不一致。暂停 CPU 不等于所有应用数据已按业务语义提交；数据库或任务协议可能还需要应用协作。

**写时复制与缺页。**普通文件后端恢复可以按需映射客户机内存，读到未驻留页时才加载，写入产生私有页面。恢复 API 很快，不意味着应用首次请求已经把需要的页面读入。[快照官方说明](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

**克隆唯一性。**从同一状态恢复多个实例，也可能复制实例标识、用户态随机数状态、令牌和连接信息。唯一性需要恢复后重新建立，不能假定换一个宿主进程 ID 就完成了处理。

## 3. 快照边界

Firecracker 保存客户机内存以及 KVM/虚拟设备状态。**磁盘文件由集成者管理，不会因为调用快照接口就自动获得一份一致的磁盘副本。**宿主 TAP、网络策略、外部数据库、监控配置等也有各自的管理和重建要求。

可以设计一份平台快照清单：Firecracker 与快照格式版本、CPU/架构条件、内核信息、内存文件、状态文件、关联磁盘版本、外部资源描述、应用就绪点及校验信息。此清单是课程提出的管理方案。

同一宿主同一版本恢复是第一步。跨宿主、跨 CPU 或跨内核恢复要建立兼容性矩阵并实测，不能默认任意迁移。网络连接不保证延续，已建立的 vsock 连接在恢复过程中会重置，需要应用重连。快照文件属于可信输入，CRC 不是来源认证。

## 4. 实验：先恢复一次，再克隆两份

1. 在可信测试客户机中运行一个在内存里递增计数、可查询状态的小程序，避免仅用磁盘文件证明“恢复了内存”。
2. 让应用停止外部写入并按需要同步磁盘，然后按文档暂停 VM、创建完整快照；在保持暂停时取得对应磁盘副本，形成一致的实验材料。
3. 记录文件清单，结束原测试实例，在同一兼容环境下的新 Firecracker 进程中加载快照，恢复执行并重新建立查询连接。
4. 比较计数状态、数据盘内容和应用就绪时间；分别记录加载完成与首次成功请求时间。
5. 选做：恢复两个克隆，为它们准备独立可写盘和明确隔离的网络资源，验证实例标识、输出、网络及写入互不串扰。
6. 核实快照内存文件在实例运行期的生命周期要求；本地材料留存到所有关联实例结束后再回收。

先学完整快照，增量快照属于进阶：必须明确基线、脏页跟踪和合并/恢复方式，不能把增量文件当成独立完整内存镜像。

## 5. 验收

交付“已保存、由外部管理、恢复后重建”三类状态清单。提供新进程恢复内存状态的证据，以及一次应用连接重建记录。能够说明实验尚未验证哪些兼容条件。
