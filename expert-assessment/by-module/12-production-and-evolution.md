## Q12-01 · 版本发布

**题目**

升级客户机内核后，10% 的环境无法联网，另外一部分只能冷启动不能恢复旧快照。请设计版本矩阵、灰度和回滚方案。哪些对象应作为一个兼容版本组发布，哪些状态不能简单回滚？

**参考答案**

1. 绑定 Firecracker/jailer、客户机内核/rootfs、设备配置、guest agent 协议、快照格式与创建环境。
2. 网络故障按版本组、架构、驱动与配置分组；快照兼容性独立验证。
3. 灰度以应用行为、失败率、恢复正确性为准。

**深入追问**

新版本写出的快照或业务格式旧版本读不了，灰度失败时怎样回滚？

**追问参考答案**

先区分代码切换、快照兼容和数据迁移；保留版本路由与兼容执行池，按合同迁移或重建状态。灰度前需要读写兼容测试与失败路径；无法反向迁移的对象不能靠替换二进制恢复。停止继续产生不兼容状态并明确受影响任务的恢复或终止方式。

**面试官核验提示**

新镜像已经写入新版数据结构或产生外部副作用，还能只切回旧二进制吗？候选人应区分执行环境回滚与业务数据迁移。

**核验证据**

给出一张版本读写矩阵和一次灰度失败后的对象处置清单。

**常见误区**

仅保留旧二进制就承诺所有状态可回退。

## Q12-02 · 选型论证

**题目**

团队正在选容器、用户态内核隔离、microVM 或已有托管沙箱。请选择至少两条你熟悉的路径，用相同工作负载、权限边界和成本口径设计 POC。说明它们对 RL reset/fork、长会话、调试、兼容性与运维的适配；什么新证据会让你改变选型？不要求背厂商宣传数字。说明 containerd/runc、gVisor、Firecracker 与 E2B、OpenHands、verl 分别能承担哪一层职责，避免把不同层的组件当作直接替代品。

**参考答案**

1. 先在同一层比较方案：runc/普通容器、gVisor 和 Firecracker 比较执行隔离与兼容；E2B/集群控制面比较环境管理；OpenHands、Harbor、verl 分别承担执行框架、评测和训练衔接。
2. 固定 POC 的任务分布、资源、网络与工具权限、会话长度和质量目标，比较冷/热路径、reset/fork、长尾、失败、资源时间与运维成本。
3. 一个可行初选是优先满足必须的隔离与兼容条件，再在通过条件的实现中比较成本。所需 syscall 不支持、快照恢复不成立或长会话成本不可接受，都是修改初选的依据。
4. 把迁移现有工作区、版本兼容、调试与维护责任写进方案。未运行的路径标记为未知；上游宣传数字和另一个硬件上的测试不直接作为本项目 SLO。

**深入追问**

有人建议“用 OpenHands 替换 Firecracker，就不用维护沙箱了”，如何评审？

**追问参考答案**

先拆分 Agent 执行框架、工具/工作区、沙箱平台与底层运行时职责。框架可使用某种工作区或远程环境，但它的存在不会自动提供产品要求的隔离与生命周期合同。评审实际部署模式、信任边界和依赖，判断哪些维护工作被转移、保留或新增，再做同条件 POC。

**核验证据**

画出分层组件图，说明哪些组件可替换、哪些需要配合及对应验证。

**源码检查点**

以需求驱动分层选型。接受同层等价项目；要求明确版本、实验环境、适配成本与未验证假设，不以熟悉品牌数量决定得分。

## Q12-03 · 一项可核查的贡献

**题目**

选一个实际负责过的运行时/Harness/沙箱模块或公开贡献，说明原问题、你具体修改了什么、最难的失败、验证过程、上线或维护结果，以及现在会怎样改进。可以使用脱敏本地材料；不要求提供公司源码或有知名开源履历。

**参考答案**

本题核验个人经历，没有统一的项目名称或指标答案。完整回答应包含以下可核查内容。

1. 原问题：明确触发条件、用户影响、原行为及承担的责任；区分个人工作与团队其他成员的工作。
2. 实际改动：说明修改的状态、协议或代码路径，为什么选该方案，以及放弃的方案有哪些代价。
3. 失败与验证：给出一个曾推翻自己假设的证据、复现步骤、修复前后结果，以及仍未覆盖的情况。
4. 发布与维护：说明实际灰度、回退、运行指标与后续维护。可以用脱敏设计或现场等价实现证明技术理解；未知的履历事实单独待核查，不需要外发公司源码。

**深入追问**

候选人不能展示公司代码，也没有公开 PR，怎样继续核验其实际贡献？

**追问参考答案**

可以现场追踪公开代码、复现同类问题，或用脱敏设计与简化实现讲清本人负责范围、失败假设、修复和验证。要求能应对条件变化并解释取舍；没有公开材料不等于没有能力。无法核验的履历事实标为待核查，不推断诚信，也不要求外发受限源码。

**核验证据**

围绕一个具体故障追问前后行为、个人修改、测试与上线结果，再做等价小型验证。

## Q12-04 · 节点维护与生产演进

**题目**

集群需要紧急升级宿主内核，同时运行长会话与 RL rollout。请设计节点停止接单、排空、检查点/迁移、容量预留、灰度、回滚和失败处理。哪些会话能够继续，哪些必须重启或报告结果不确定？用哪些业务和基础设施指标决定是否继续升级？

**参考答案**

1. 先明确维护期限、任务可中断性、状态与恢复兼容矩阵，停止或限制新准入，等待可完成任务并处理有界排空。
2. 跨宿主恢复不能默认兼容；可以保留兼容池、在安全边界检查点、重建环境或按合同终止。
3. 用应用就绪、有效轨迹、失败分类、长尾和资源指标灰度，记录控制面与节点版本。
4. 回滚程序不会撤销数据格式变化或外部副作用，要求说明不可逆边界。

**深入追问**

维护必须在十分钟内完成，但有任务还需一小时且无法恢复，该怎么处理？

**追问参考答案**

先明确维护紧迫性、任务合同与可用容量，停止受影响节点新准入；按风险与业务优先级选择隔离、迁移可恢复任务、保存已有产物或终止不可恢复任务。对在途外部操作保留不确定结果并对账，向调用方提供真实状态。不能同时无条件保证硬维护期限和所有任务无损继续。

**核验证据**

给出十分钟执行计划、决策条件和失败后的用户可见状态，说明无法满足的保证。

## 如何判断是否精通

每题沿用统一题库的 0–4 分，不增加一套总分：

| 分数 | 判断依据 |
| --- | --- |
| 0 | 核心机制错误，澄清后仍无法建立正确解释 |
| 1 | 能说术语，不能解释行为与边界 |
| 2 | 正常流程与主要机制正确，失败处理不完整 |
| 3 | 能处理失败、解释取舍并提出可执行验证 |
| 4 | 达到 3 分，且能给出可核查证据、回答条件变化后的追问 |

建议判为“本模块已展示精通”：全部题目已覆盖、每题至少 3 分、至少两题达到 4 分，并完成下面的现场核验；关键边界经过澄清后没有遗留错误。仅口述或未覆盖全部题目，记录“已覆盖部分达标/待验证”，不推算整个模块精通。评分门槛是本课程建议，不是行业认证。

现场源码、mock、真实运行时和生产经验分别记录。真实运行时或生产能力的主张，需要相应证据；不能用一次 mock 或高口述分替代。候选人采用同层、同等深度的其他开源项目也可得分。

**课程项目核验：**Q12-01/Q12-02/Q12-03/Q12-04 使用真实负责范围与比较数据作答，不把阅读多个项目等同于维护这些项目的经验。

**现场核验任务：**提交一张同条件 POC 对比表与版本矩阵，演练维护期限内不能无损恢复的任务处置。

**本模块关键误解：**更换二进制可回滚全部状态；不同架构层组件直接互相替代；用项目名气替代个人证据。
