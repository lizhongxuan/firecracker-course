## Q01-01 · 调用路径

**题目**

客户机 Python 程序执行一次文件写入。从客户机系统调用开始，解释它可能经过哪些内核、virtio、VMM 与 KVM 路径。客户机每个系统调用是否都会成为宿主系统调用或 KVM 用户态退出？请画图并说明哪些路径取决于设备配置。

**参考答案**

1. Python 调用 write 后，系统调用首先进入客户机 Linux 内核；vCPU 通过 KVM 执行客户机代码。普通客户机 syscall 不等于调用 Firecracker API，也不必逐次退出到 VMM 用户态。
2. 若数据只进入客户机页缓存，write 可以先返回。需要访问虚拟块设备时，客户机驱动准备 virtio 队列，设备通知触发相应后端处理；KVM 退出中有些在内核处理，有些需要用户态 VMM 处理。
3. 进程内块设备后端读取描述符、检查客户机内存范围并执行宿主文件/设备 I/O，随后更新完成队列并通知客户机。外部设备后端或网络文件系统会改变这条链，需按实际配置说明。
4. vCPU 负责推进客户机指令，设备后端负责虚拟设备请求，宿主内核与存储负责实际 I/O；它们的完成与持久化语义需要分别核对。

**深入追问**

write 返回成功，随后客户机或宿主突然掉电，文件一定保存了吗？

**追问参考答案**

不一定。write 成功通常只说明某一层接受了数据；要区分客户机页缓存、文件系统提交、virtio 完成、宿主缓存与底层介质。即使应用调用 fsync，也要核对客户机、虚拟块设备与宿主后端的 flush/cache 合同。分别设计客户机崩溃和宿主掉电场景，不能把一次正常关闭实验当作持久性证明。

**面试官核验提示**

同一程序换成缓冲写、同步写和网络文件系统，图如何变化？要求指出队列或设备后端源码，并解释哪些部分只是示意。

**核验证据**

画出读写与持久化确认路径，给每一层标出失效后可能丢失的状态。

**常见误区**

声称 Firecracker 逐条模拟所有客户机指令，或每次客户机 syscall 都必须进入 Firecracker HTTP API。

## Q01-02 · 环境判定

**题目**

一台 x86_64 Linux 云主机有 `/dev/kvm`，当前用户能读写，但 microVM 创建失败；开发者使用的是 Apple Silicon Mac。给出按证据推进的排查顺序。如何区分架构/镜像错误、KVM 能力缺失、权限与上层虚拟化问题？哪些观察不足以单独下结论？

**参考答案**

1. 先拿实际报错、运行架构、二进制与镜像格式，再验证 KVM 打开/能力查询/创建 VM 等失败层；核对权限、内核配置、嵌套虚拟化和所用版本。
2. Mac 架构不能决定 Linux 服务器下载哪种资源。

**深入追问**

同一个测试程序以 root 能创建 VM，普通用户失败，是否可以直接判定 KVM 不支持虚拟化？

**追问参考答案**

不能。先固定相同二进制、配置和环境，定位失败的系统调用与 errno；再检查设备访问、所属组、目录/socket 权限、服务隔离及安全策略。设备能打开也不代表后续操作一定获准。修复应针对失败条件给最小权限，而非长期将服务整体改成 root。

**面试官核验提示**

`/dev/kvm` 可读写但特定 ioctl 失败时，要如何用 errno、能力查询和宿主日志缩小范围？有些内核配置内建 KVM，不能只凭 `lsmod` 没结果就断言不可用。

**核验证据**

提供排查决策树：每个观察结果都能排除一个假设，并指出下一步证据。

**常见误区**

第一步就把设备 chmod 为全员可写，或仅看到 Linux 与 `/dev/kvm` 就宣称环境兼容。

## Q01-03 · Agent 边界

**题目**

模型服务在外部，宿主机运行 orchestration controller，microVM 内运行 shell 和 Python，宿主工具代理持有业务凭证。请画出信任边界，说明哪些组件可以处理不可信文本、哪些组件可以授权操作。把 agent 主循环移进 VM，安全保证发生了什么变化？

**参考答案**

1. 模型输出、文档、guest 和 guest agent 的数据均不能自行升级权限。
2. 可信控制器保存用户意图，工具代理用可信身份与策略约束副作用，执行环境限制计算和数据访问。
3. 把循环放进 VM 会改变进程和数据暴露面，但不会让不可信模型输出成为授权。

**深入追问**

模型与主循环都移进 VM，但工具代理仍持有高权限凭证，哪些风险仍在？

**追问参考答案**

VM 里的调用仍是不可信请求。代理必须从可信连接或能力凭据确定主体，绑定任务、目标资源、动作、参数与当前权限，不能相信请求自报的 tenant ID 或 approved 字段。隔离改善了宿主进程暴露面，未授权业务操作、额度滥用和允许通道中的数据泄露仍需授权层约束。

**面试官核验提示**

代理不把密钥交给 guest，却接受任意业务参数，哪些风险仍存在？能区分“保护宿主”与“保护用户在外部业务系统中的权限”。

**核验证据**

画出一条没有 VM 逃逸、但可能发生越权的调用链，并在可信端放置具体拒绝点。

**常见误区**

认为进程进入 microVM 后就无需工具鉴权或提示注入处理。

## Q01-04 · 方案选择

**题目**

产品希望支持 30 分钟交互式 coding agent、依赖安装、代码运行和受控文件产物。比较普通容器、microVM 与进程级隔离方案。明确比较所采用的威胁模型、兼容性、运行成本、运维与验证方式，不用品牌名代替结论。可用 runc、gVisor、Firecracker 或等价实现作例子，说明它们分别位于哪一层，并提供一条源码或官方架构依据。

**参考答案**

1. 先确定代码是否可信、租户边界、必需的系统调用/设备、工作区持久性、网络权限与延迟目标。30 分钟会话还要统计等待模型的比例和常驻内存成本。
2. 普通容器共享宿主内核，镜像生态与运维通常较直接；适用于其内核共享风险与权限边界可被接受的场景。namespace、cgroup 和降权分别提供不同限制。
3. gVisor 一类应用内核方案改变应用与宿主内核的交互边界，应实测所需功能与 I/O 开销；不能把所有“进程隔离”实现视为同一保证。
4. Firecracker microVM 具有客户机内核与虚拟设备边界，需要管理内核、rootfs、网络、就绪和快照兼容。若选择它，仍要实现业务工具授权和会话状态管理。
5. 一个可行决策是为不可信任意代码选满足威胁模型的强隔离后端，为可信受限工具用较轻执行路径；用相同任务、权限与成本口径验证，而不承诺某种后端在所有场景最好。

**深入追问**

选型后发现任务依赖后台服务、特殊系统调用和网络文件系统，如何改变决策？

**追问参考答案**

先把依赖转成可执行的兼容性用例，在相同资源与权限下验证所选版本。区分运行时不支持、配置受限和应用假设错误，再比较修改应用、限制产品范围或改用另一后端的代价。迁移方案还需覆盖工作区、网络与运行中会话；无法兼容时明确失败，不能为了跑通而默认开放宿主高权限。

**面试官核验提示**

分别给可信单租户开发与不可信多租户执行选择方案，定义验证标准及替代路径。

**核验证据**

交付比较矩阵和一个使原选型失效的实验条件，说明取舍与替代方案。

**常见误区**

单凭一个启动耗时或品牌就判定所有场景的优劣。

**源码检查点**

核对运行时层次与系统调用路径。能够用 containerd/runc、gVisor 或其他实现解释职责即可；不要将平台、VMM 和 Agent 框架放在同一层简单排名。

## 如何判断是否精通

每题沿用统一题库的 0–4 分，不增加一套总分：

| 分数 | 判断依据 |
| --- | --- |
| 0 | 核心机制错误，澄清后仍无法建立正确解释 |
| 1 | 能说术语，不能解释行为与边界 |
| 2 | 正常流程与主要机制正确，失败处理不完整 |
| 3 | 能处理失败、解释取舍并提出可执行验证 |
| 4 | 达到 3 分，且能给出可核查证据、回答条件变化后的追问 |

建议判为“本模块已展示精通”：全部题目已覆盖、每题至少 3 分、至少两题达到 4 分，并完成下面的现场核验；关键边界经过澄清后没有遗留错误。仅口述或未覆盖全部题目，记录“已覆盖部分达标/待验证”，不推算整个模块精通。评分门槛是本课程建议，不是行业认证。

现场源码、mock、真实运行时和生产经验分别记录。真实运行时或生产能力的主张，需要相应证据；不能用一次 mock 或高口述分替代。候选人采用同层、同等深度的其他开源项目也可得分。

**课程项目核验：**Q01-01/Q01-04 使用上述调用路径和对比表作答；不能用某个项目的名称替代实际隔离机制。

**现场核验任务：**用一个文件写入请求画调用路径，再把高权限工具放入图中，标出隔离与授权分别在哪生效。

**本模块关键误解：**把每个 guest syscall 当作宿主 syscall；认为 VM 自动解决工具授权。
