## Q08-01 · seed 相同但结果不同

**题目**

同一任务、镜像和 seed 重跑两次，工具调用次序、耗时和最终结果仍不同。设计 Harness 的可复现目标、事件协议与 record/replay。区分真实重新执行、录制结果回放和重新让模型生成；哪些保证可做，哪些不能仅靠 seed 或 VM 快照实现？

**参考答案**

1. 定义复现粒度：相同事件、相同工具返回、相同最终产物，还是逐位相同执行。
2. 记录版本、输入、随机流、时间来源、工具请求/返回、模型输出及事件顺序；必要时使用虚拟时钟、固定 mock、受控网络和调度约束。
3. 录制结果回放不再次执行真实工具，可以复现受控输入序列并定位分歧；真实重新执行受到文件、网络、时钟和并发等影响；重新采样模型又增加一类变量。
4. seed 或 VM 快照都不能单独固定外部世界与所有并发行为。
5. 回放能检测动作/参数/版本不匹配，指出第一个分歧，而不是不管输入是什么都返回录制成功。
6. 新版本对照时应明确哪些调用可以接受语义等价、哪些要求精确匹配。

**深入追问**

新版本请求的工具参数与录制时不同，但“看起来意思相同”，回放可以继续吗？

**追问参考答案**

默认应报告首次分歧；若允许语义等价，必须事先定义可验证的规范化和比较规则，并保留原始请求及规则版本。不能临时凭直觉匹配成功结果。回放使用录制返回值，不重新产生工具副作用；真实重跑应作为另一种明确模式。

**核验证据**

演示参数变化和版本变化两种分歧，指出哪个事件首先不匹配。

## Q08-02 · 分数提升是否可信

**题目**

新沙箱版本上线后，benchmark 成功率从 62% 升到 75%，但 agent 可以修改工作区、运行任意命令，评分也在环境中完成。如何判断是模型/环境真实改善、评分器被影响、任务泄漏、重试口径改变，还是基础设施失败被漏计？设计评分器边界、结果来源、版本记录和对照实验。可用 Harbor 或等价评测框架描述 task、trial、verifier 与结果记录，指出评分权限及异常统计的实际边界。

**参考答案**

1. 验证评分脚本、数据、结果通道的权限边界；任务代码不能直接改写可信奖励。
2. 可采用独立验证环境、受控产物导入、结束写入后的检查或具备足够隔离的其他设计，不能认为“在同一 VM 换个目录”就必然不可篡改。
3. 单看 reward 文件也不能证明结果来源可信。
4. 固定任务/数据、策略、采样和预算条件，记录评分器版本、重试、超时、基础设施失败与缺失样本。
5. 做有足够样本的对照，检查泄漏、作弊和不应成功的负向用例。
6. 环境改善也可能是真实产品收益，但需区分模型能力提升与环境配置变化。

**深入追问**

成功率上涨只是因为失败任务现在自动重试三次，如何比较两个版本？

**追问参考答案**

同时报告固定原始任务集上的最终成功率、每次尝试结果、总预算与成本，保留超时、基础设施错误和缺失样本。固定重试与预算合同后做配对或可比对照，才能区分模型、环境和策略变化。多次尝试的最终成功率不能直接冒充单次执行能力提升。

**面试官核验提示**

怎样防止 agent 看到隐藏验证信息？如果评分器本身非确定，怎样估计波动？不能把所有分数上涨都视为沙箱性能优化的证据。

**核验证据**

用一张包含原任务、全部尝试、结束原因和费用的表，重算两种统计口径。

**源码检查点**

追踪任务、验证环境和可信结果读取链；区分任务失败、评分异常与环境失败。独立 verifier 的存在本身不能证明输入、挂载与结果来源都可信。

## Q08-03 · 命令重试还是工具失控

**题目**

某个 agent 延迟和外部 API 成本持续上升，但 microVM CPU 与内存正常。请设计能区分模型思考、工具排队、重复调用、审批等待、数据传输、VM 恢复与业务失败的观测方案，同时控制敏感数据暴露。

**参考答案**

1. 关联会话/任务/attempt/tool-call/VM/审批，分段测模型等待、队列、工具执行与重试、恢复、数据传输和人工等待。
2. 记录调用次数、预算、重试原因与去重命中；敏感文本和 token 不必进入日志，保留最小必要元数据。

**深入追问**

日志出现两条相同工具调用记录，能认定外部 API 被调用了两次吗？

**追问参考答案**

不能，可能是日志重放、采集重复、请求重试或真实重复执行。关联调用 ID、attempt、代理派发记录和外部回执，区分请求受理、实际派发和已确认效果。证据不足时保留不确定状态，不能按日志行数直接计费或判定事故。

**面试官核验提示**

工具名称不变但参数改变如何关联？重复执行和重复记录如何区分？避免高基数标签拖垮指标系统，必要细节放受控审计或 trace。

**核验证据**

画出重复记录但只执行一次、以及真正执行两次的两条时间线。

**常见误区**

只看 Firecracker CPU/内存，或把完整凭证与所有用户文本写日志当作默认排障方式。

## Q08-04 · 会话恢复不等于进程恢复

**题目**

agent 的 VM 回到十分钟前，但控制面保存着最新对话、用户审批和工具执行记录；外部系统也已产生写入。请设计恢复协议，明确哪些历史状态必须继续向前、哪些可以回退，以及如何处理尚无确定结果的工具调用。

**参考答案**

1. 控制面的授权、撤权、已提交工具调用与审计记录保持可信的单调推进，VM 快照不能把它们回滚。
2. 恢复引入新代次并握手对账，旧命令不直接重播；把已完成、未派发和结果不确定分开。

**深入追问**

VM 回退后本地文件显示操作未完成，但外部服务确认已成功，该相信谁？

**追问参考答案**

两份状态描述的是不同时间点。先依据可信工具账本与外部结果核对操作身份，再向前修复本地状态或重建环境；不因旧文件缺失就重复产生副作用。必要时按业务协议补偿，无法确认时保留不确定结果。撤权和审计也不能随 VM 回退。

**面试官核验提示**

恢复点之后发生的外部写入如何验证或补偿？若 API 没有查询或幂等机制，应明确人工核对/不自动重试等产品语义，而不是重放整个对话。

**核验证据**

展示一次恢复握手，区分已完成、未派发和结果未知三类操作。

**常见误区**

把“重放模型消息”视为恢复业务副作用的通用方法。

## Q08-05 · Harness 事件契约

**题目**

模型、环境、工具代理和评分器分别产生事件，可能乱序、重复、迟到或缺失。设计事件字段、因果关系、持久化和去重规则，使一次 rollout 能被重建并定位首个分歧。怎样防止迟到事件覆盖任务终态，怎样避免把敏感内容直接写进指标？可选 OpenHands 的动作/观测事件作为一个输入源，说明映射到跨组件事件协议时还缺哪些关联信息。

**参考答案**

1. 事件至少带 event_id、来源、schema 版本、task/episode/attempt/branch/step/tool-call 关联和事件类型；父事件或等价关系表达因果，时间戳用于观测而非独自决定顺序。
2. 对已接纳事件保留持久记录，以稳定身份去重；发现缺口或未知前驱时等待补齐、标记不完整或按明确规则处置，不凭空推造事件。
3. 可信状态机根据当前执行代次与合法转换提交结果。迟到旧事件可保留为审计事实，但不能覆盖已经合法提交的终态。
4. 回放从指定版本和输入开始，逐步核对动作、参数、结果与状态，定位首个分歧；重建依赖账本和因果关系，不能只按跨机器时钟排序。
5. 指标保留低基数聚合；每次调用的详细 ID 与必要正文放受控 trace/审计中。事件去重只解决记录重复，不自动保证外部工具效果恰好一次。

**深入追问**

旧 attempt 的“成功”事件晚于新 attempt 的“失败”到达，最终结果按时间戳取最新可以吗？

**追问参考答案**

不能，接收时间和机器时钟不决定合法执行权。由可信状态转换、当前执行代次和结果提交规则决定是否接纳；旧事件可以进入审计，但不能直接覆盖当前终态。重复事件按稳定身份去重，缺失事件单独标记，不能靠排序补出不存在的因果关系。

**核验证据**

给出乱序事件序列，逐条说明状态是否改变及审计是否保留。

**源码检查点**

检查会话内事件与跨模型、工具、环境、评分器的事件范围差异。要求明确 task/attempt/step、来源、版本与因果信息，并验证重复和迟到事件处理。

## 如何判断是否精通

每题沿用统一题库的 0–4 分，不增加一套总分：

| 分数 | 判断依据 |
| --- | --- |
| 0 | 核心机制错误，澄清后仍无法建立正确解释 |
| 1 | 能说术语，不能解释行为与边界 |
| 2 | 正常流程与主要机制正确，失败处理不完整 |
| 3 | 能处理失败、解释取舍并提出可执行验证 |
| 4 | 达到 3 分，且能给出可核查证据、回答条件变化后的追问 |

建议判为“本模块已展示精通”：全部题目已覆盖、每题至少 3 分、至少两题达到 4 分，并完成下面的现场核验；关键边界经过澄清后没有遗留错误。仅口述或未覆盖全部题目，记录“已覆盖部分达标/待验证”，不推算整个模块精通。评分门槛是本课程建议，不是行业认证。

现场源码、mock、真实运行时和生产经验分别记录。真实运行时或生产能力的主张，需要相应证据；不能用一次 mock 或高口述分替代。候选人采用同层、同等深度的其他开源项目也可得分。

**课程项目核验：**Q08-01/Q08-02/Q08-05 使用事件与评分证据回答。项目宣称可复现不能代替对当前后端、模型和工具状态的核验。

**现场核验任务：**对一组重复/乱序事件重建执行，再改变一个工具参数，指出回放首次分歧；核查评分来源。

**本模块关键误解：**固定 seed 保证外部世界确定；任务可任意改写可信奖励；只报告成功样本。
