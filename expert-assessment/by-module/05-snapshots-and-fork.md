## Q05-01 · 一致性恢复

**题目**

任务在更新数据库文件时，管理层暂停 microVM，保存内存和 VM 状态，再复制数据盘。什么时候这能形成可用检查点，什么时候还不够？请讨论应用一致性、块设备 flush、缓存语义和外部数据库事务。

**参考答案**

1. 先声明要恢复到什么一致性：应用可恢复的崩溃状态、应用检查点，还是跨系统业务状态。数据库是否能利用日志恢复，取决于自身事务和持久化合同。
2. 内存、VM/设备状态与磁盘应属于同一可恢复切面；暂停 vCPU 不足以推断所有后端 I/O 已停止。检查所选版本的快照流程、在途 I/O 排空和外部后端协调要求。
3. 核对客户机 fsync/flush、设备缓存模式、宿主文件和底层介质的持久性；需要应用级一致性时执行相应检查点或静止协议。
4. 把状态、内存、磁盘版本与配置绑定到不可变 manifest，材料完整且校验通过后才发布检查点，避免恢复到各自完整但互不匹配的文件。
5. 外部数据库或业务 API 不随 VM 快照回退。恢复后必须用可信工具/事务记录对账，对未决操作按查询、幂等、补偿或结果不确定的合同处理。

**深入追问**

三个快照文件各自校验都通过，为什么组合起来仍可能恢复错误？

**追问参考答案**

单文件完整性不证明它们属于同一状态切面。协调应用/设备在途操作、内存与磁盘版本，生成绑定全部对象的不可变 manifest，并在材料完整后发布可用状态。部分生成失败的检查点不能对外使用。具体排空和持久化要求按后端与版本核对。

**面试官核验提示**

本仓库暂停时仍可能有内核完成在途异步块 I/O；快照创建会排空相应请求，外部 vhost-user 后端另需协调。要求查版本文档解释“暂停”与“可复制磁盘”的区别。`Unsafe` 与 `Writeback` 的持久性语义也要核对。

**核验证据**

画出快照生成、验证、发布和失败回收时序，展示错配版本会被拒绝。

**常见误区**

认为暂停立即冻结所有外部存储，或恢复 VM 能回滚外部数据库。

## Q05-02 · 看似恢复成功

**题目**

加载快照 API 成功，但业务数据回到了错误版本，网络连接失败。请列出快照包含什么、依赖什么、恢复后需要重建什么，并设计能够发现“表面成功、语义错误”的验收。

**参考答案**

1. 区分 guest 内存与 VM/KVM/设备状态、外部磁盘版本、TAP/网络、vsock 后端、监控与外部业务状态。
2. 连接不保证延续，已建立 vsock 连接要按版本语义重建。
3. 恢复 API 成功仅说明某一层加载成立，业务验收要查询内存标记、数据版本、身份、连接和实际请求。

**深入追问**

内存、状态和磁盘摘要匹配，但 manifest 属于另一租户，完整性校验够吗？

**追问参考答案**

不够。摘要用于检测内容匹配，还需验证 manifest 的可信来源、所属主体、使用授权和当前有效性。控制面把租户、模板、实例与对象版本关联，恢复后重建实例身份及受限权限。不能由 guest 自报身份或对象存储路径名决定授权。

**面试官核验提示**

如何防止状态文件与内存/磁盘错配？建立不可变 manifest、摘要和可信来源，并维护运行期引用；CRC 不是认证来源。

**核验证据**

给出内容完整但主体错误的负向用例，指出恢复前与恢复后的检查位置。

**常见误区**

把磁盘副本、网络外部状态和所有连接都视为 snapshot API 自动保存恢复的内容。

## Q05-03 · 迁移兼容性

**题目**

将快照从 Intel 节点迁至 AMD 节点，同时升级 Firecracker 和宿主内核，团队想用 CPU template 解决全部问题。请说明需要分别验证哪些条件，如何构建兼容性矩阵，失败时怎样回退。

**参考答案**

1. CPU 模板限制或配置客户机可见能力，并不消除架构、厂商语义、MSR/CPU 状态、KVM 内核、设备模型和快照格式差异。
2. 按来源/目标 CPU、内核、Firecracker、设备配置建立矩阵，测恢复与负载正确性。

**深入追问**

目标节点无法恢复旧快照，直接冷启动是否属于无损回退？

**追问参考答案**

只有所需业务状态已持久化且可重建时才可能满足同等业务合同。冷启动不会恢复仅在内存中的会话或进程状态；外部已执行但结果未知的操作也不能直接重试。可选择保留兼容节点、迁移应用状态或显式终止，向调用方说明数据和副作用边界。

**面试官核验提示**

如果一个组合不能恢复，是保留兼容节点、迁移应用状态、重建模板还是冷启动？冷启动回退也要说明会丢失哪些仅在内存中的状态。

**核验证据**

列出恢复失败后的三条可选路径，以及每条会失去或保留的状态。

**常见误区**

“用了 CPU template 就可跨任意硬件、架构和版本恢复”。

## Q05-04 · 模板里的秘密

**题目**

为了缩短准备时间，模板 VM 已登录业务服务、取得短期令牌、初始化用户态随机数生成器，并等待下一条工具指令。该模板被克隆给多个租户。指出问题，设计可复用的快照边界和恢复后的初始化协议。

**参考答案**

1. 模板停在不含租户秘密和任务身份的通用初始化边界。
2. 恢复后建立新的实例身份和执行代次、申请适当凭证、处理用户态随机数状态、重建连接、加载当前策略，再接收任务。
3. 短期 token 在有效期内仍不能跨租户共享。

**深入追问**

分支需要可复现随机探索，同时需要安全的令牌与唯一 ID，能共用一个固定 seed 吗？

**追问参考答案**

不应把可复现实验随机流当作安全凭证随机源。实验记录基础 seed、分支派生规则与版本；安全能力由可信端独立签发，绑定主体和作用域。恢复后检查应用缓存的 nonce、ID 和连接状态，不能只重置内核随机状态就推断所有用户态状态已更新。

**面试官核验提示**

内核随机状态被刷新后，应用内 PRNG、缓存的 nonce/ID、连接池与浏览器登录态是否一定正确？要求逐层说明，不靠一个 VMGenID 或换 PID 覆盖全部。

**核验证据**

分别画出实验随机流与安全凭证来源，验证分支可复现且不会共享授权。

**常见误区**

克隆已登录模板，仅修改 hostname 就交给不同租户。

## Q05-05 · 同一点分出 32 条路径

**题目**

一个 agent 已执行到第 12 步，平台要从该点派生 32 个分支，各自尝试下一步工具调用。请定义 `fork(checkpoint, branch_spec)` 的语义，解释 VM、磁盘、对话、随机状态、记忆、权限、在途工具和外部服务分别如何处理。如何保证“相同起点”并允许分支获得不同随机序列？若复用 E2B 一类平台的 VM fork，哪些 Agent 状态与副作用合同还需要你实现？请给出平台边界与上层接口。

**参考答案**

1. 先明确 checkpoint 的一致切面：客户机状态、文件/磁盘版本、对话前缀、工具账本、记忆引用、环境版本和未完成操作。
2. 分支拥有独立身份、私有写入、能力与预算；共享不可变基础。
3. 父子状态和外部服务需明确定义复制、引用、mock 或禁止分叉的条件。
4. 相同初始任务状态与不同随机探索并不冲突；记录基础 seed 及可复现的分支随机流，避免把同一用户态 RNG/令牌盲目复制。
5. 工具请求在途时可排空、等待或记录不确定状态，但不能复制未决外部事务就声称分支独立。
6. Firecracker 快照是底层机制，不自动实现所有业务状态的 fork。
7. 宿主 `fork()` 共享/继承 KVM 文件描述符也不能当作受支持的通用 VM 克隆方案；必要时核对 [KVM API 限制](https://docs.kernel.org/virt/kvm/api.html) 与 [快照文档](../../../../docs/snapshotting/snapshot-support.md)。

**深入追问**

父分支正在调用一个不可撤销的扣费接口，此时收到 fork 请求，怎么办？

**追问参考答案**

不能把一笔未决外部操作复制成多个独立事实。可等待其结果、在允许的检查点排空，或拒绝在该位置分叉；也可把未决操作作为父任务账本中的共享事实，并限制子分支继续执行的条件。若产品需要独立探索外部效果，应使用明确的模拟或隔离环境，不能声称快照复制了外部系统。

**核验证据**

给出父任务、工具账本和两个子分支的时序，明确不确定结果由谁负责。

**源码检查点**

用所选版本区分 Firecracker 快照、平台磁盘/内存恢复与 Agent 分支合同。核对父子身份、私有写入与授权，不能从 fork API 名称推断完整会话或外部服务已被复制。

## Q05-06 · 分支成本与回收

**题目**

假设模板共享驻留内存为 384 MiB，每个分支额外私有内存 48 MiB，共 32 个分支，且模板保留。估算页面内存，再列出未包含的开销。若 31 个分支取消，只保留一个分支的工作区结果，如何保证回收正确？“选择获胜分支”能否通用地合并其全部进程和外部状态？

**参考答案**

1. 给定共享页持续驻留且模板保留的简化假设，页面预算为 `384 + 32 × 48 = 1920 MiB = 1.875 GiB`。
2. 还要计入每进程/VMM、页表、队列/缓冲区、磁盘私有写入、文件缓存、宿主余量与更多脏页，不能把算式当生产占用保证。
3. 父模板和兄弟分支有引用关系，按真实使用情况回收，处理部分创建失败和取消。
4. 可将获胜分支的工作区产物作为新基线，或直接继续获胜实例；不存在无需业务协议即可合并所有内存和外部副作用的通用操作。

**深入追问**

32 个分支各自私有页从 48 MiB 增长到 300 MiB，页面预算变成多少？

**追问参考答案**

沿题设的简化模型计算为 384 + 32 × 300 = 9984 MiB，即 9.75 GiB；仍未包含 VMM、页表、缓存等开销。写入会改变私有页面和共享收益，需要实测分布并实施准入与预算控制。不能把初始化时的共享比率用作整个会话生命周期的固定成本。

**面试官核验提示**

分支不断写内存后共享收益如何变化？父分支先被删除时谁持有模板引用？只记一个引用计数但崩溃后无法对账不够。

**核验证据**

计算量纲正确，并给出私有页增长、取消和模板引用的观测方案。

## 如何判断是否精通

每题沿用统一题库的 0–4 分，不增加一套总分：

| 分数 | 判断依据 |
| --- | --- |
| 0 | 核心机制错误，澄清后仍无法建立正确解释 |
| 1 | 能说术语，不能解释行为与边界 |
| 2 | 正常流程与主要机制正确，失败处理不完整 |
| 3 | 能处理失败、解释取舍并提出可执行验证 |
| 4 | 达到 3 分，且能给出可核查证据、回答条件变化后的追问 |

建议判为“本模块已展示精通”：全部题目已覆盖、每题至少 3 分、至少两题达到 4 分，并完成下面的现场核验；关键边界经过澄清后没有遗留错误。仅口述或未覆盖全部题目，记录“已覆盖部分达标/待验证”，不推算整个模块精通。评分门槛是本课程建议，不是行业认证。

现场源码、mock、真实运行时和生产经验分别记录。真实运行时或生产能力的主张，需要相应证据；不能用一次 mock 或高口述分替代。候选人采用同层、同等深度的其他开源项目也可得分。

**课程项目核验：**Q05-02/Q05-05/Q05-06 结合恢复链和分支实验说明机制，不把官方示例中的性能数字当成本机实测结果。

**现场核验任务：**列出检查点 manifest 和父子资源关系；推演在途外部调用、分支取消与模板仍被引用的情况。

**本模块关键误解：**暂停冻结外部世界；快照保存所有磁盘/业务状态；宿主 fork 等于受支持的 VM 克隆。
