## Q03-01 · 启动结果未知

**题目**

控制器启动一个 microVM 后，在写入“已启动”状态之前崩溃；客户端因超时重试。请给出持久化记录、状态机和恢复伪代码，确保能核对已有实例、避免失控重复创建，并回收孤儿资源。可结合 E2B 或其他管理器的创建路径，标出一次远程请求和一次持久化之间的失败窗口。

**参考答案**

1. 在创建副作用前，持久化 task、attempt、instance 身份、幂等键及参数摘要、期望状态和执行代次。相同键不同参数应报冲突。
2. 用可识别的实例目录、cgroup、socket 和配置建立资源归属，创建后持续记录实际资源。进程启动与数据库提交并非原子操作，设计必须容许中间状态。
3. 恢复时先读取持久意图，再观察真实资源：存在且身份匹配则接管；确认不存在才补建；只完成一部分则继续或补偿；归属不确定时记录待核对，避免误删。
4. 对账器重复执行上述规则，并使用条件更新/执行代次拒绝过期控制者的提交。PID 要结合启动身份核对，不能单独当实例标识。
5. 注入“资源已创建、记录未完成”和“结果已保存、确认丢失”两类故障，验证没有失控重复创建、已知结果保留且孤儿资源可被发现。

**深入追问**

发现一个进程 PID 与旧记录一致，但启动时间不同，控制器该接管还是删除？

**追问参考答案**

PID 可能被复用，不能据此接管或终止。综合实例专属路径、进程启动身份、受控配置、cgroup 与执行代次核对所有权；发现无法证明归属的资源时隔离记录并进入待核对状态。创建意图和资源标签应让恢复流程能够识别属于自己的孤儿资源。

**面试官核验提示**

孤儿进程与 PID 复用如何区分？资源创建成功但清单没写入如何发现？可以使用实例专属路径、持久意图、进程启动身份和受控扫描组合，但不能盲信 PID 或 guest 自报信息。

**核验证据**

用 PID 复用和部分创建失败两个事件，演示对账不会误操作其他实例。

**常见误区**

每次超时直接创建新 VM，或把数据库“运行中”当实际状态。

**源码检查点**

沿 API、节点管理、状态存储的实际代码定位窗口。没有持久对账或可靠身份时应指出限制，不能把设计愿望说成上游已提供的保证。

## Q03-02 · 取消竞态

**题目**

执行命令、请求取消和客户机返回结果几乎同时发生。你如何定义“取消请求已接受”“进程已停止”“结果已提交”？如何处理命令派生的后台进程，以及清理阶段再次崩溃？

**参考答案**

1. 用明确的状态转换和提交顺序定义取消/完成谁胜出；取消受理不代表进程已停止。
2. 限制并处理客户机内派生任务，必要时终止整台实例；宿主工具调用另有取消与不可撤销语义。
3. 清理可重试，完成结果不被清理失败覆盖。

**深入追问**

取消返回“已受理”后，发现外部业务写入已成功，任务最终应显示什么？

**追问参考答案**

取消受理与停止执行是不同事实。按事先定义的终态提交顺序决定完成还是取消，同时保留已发生副作用及其结果；必要时显示“已取消后续执行，但已有操作生效”。不能删除成功业务记录伪装撤销，也不能让清理失败覆盖确定的执行结果。

**面试官核验提示**

取消到达之前业务写入已完成、结果稍后才到，返回什么？两种合理合同均可，但必须一致并可审计。

**核验证据**

画出取消、外部完成、结果提交三种排列，说明各自用户可见状态。

**常见误区**

kill 一个 shell PID 就保证所有副作用和后代任务消失。

## Q03-03 · 人工等待与撤权

**题目**

agent 等待用户确认 20 分钟，期间会话暂停，用户撤销了工具权限。恢复后队列里仍有原先生成的工具调用。请设计审批、任务状态、权限版本与执行检查的关系，指出检查和实际执行之间的竞态。

**参考答案**

1. 审批绑定具体主体、任务、操作、资源、参数及有效期/权限版本；可信执行端在派发前校验当前权限。
2. 恢复不能重放已经失效的授权；参数变化需要重新判定是否仍在授权范围内。

**深入追问**

执行端检查权限后、真正派发前发生撤权，双重检查能保证什么？

**追问参考答案**

两次普通读取之间仍可能有竞态。需要定义授权与执行受理的排序点，例如由可信代理以当前权限版本验证并登记派发；说明撤权对哪些新受理操作生效。已送达外部系统的在途请求是否能取消取决于对方能力，无法用旧快照或本地布尔值撤回。

**面试官核验提示**

撤权和执行如何排序？可以定义可线性化的执行受理点/代次检查；已送到外部服务的操作不保证撤回，需明确“对新派发即时生效”和在途处置的边界。仅在两端读一次布尔值不足以解决竞态。

**核验证据**

标出受理点和撤权生效边界，给出并发时序及可验证的承诺。

**常见误区**

把 VM 内保存的“approved=true”或模型文本当作当前授权。

## Q03-04 · 长任务跨版本恢复

**题目**

一个运行数小时的 agent 因节点维护暂停，恢复时 Harness、工具 schema 和技能包已经升级。你如何保留可继续执行的状态，处理旧的工具请求、记录顺序、预算、权限撤销和幂等结果？哪些版本可以迁移，哪些情况应保留旧运行环境或明确终止？

**参考答案**

1. 长任务用可持久化状态机、事件/结果账本、检查点和兼容规则支持继续执行，而非只保存聊天文本。
2. 保存任务与尝试身份、已完成步骤、环境版本、工具结果、预算和当前合法权限；恢复后对账。
3. 工具 schema/技能/状态版本迁移需要验证和明确边界；不可兼容时保留旧执行栈、重建必要状态或终止并解释，不能悄悄用新协议重放旧请求。
4. 权限撤销与已提交外部动作保持向前，不能随快照回滚。

**深入追问**

旧工具请求没有填写一个参数，新版本给这个参数增加了高影响默认值，能直接恢复吗？

**追问参考答案**

不能仅因 JSON 仍可解析就认为语义兼容。保存工具版本及当时确定的执行语义，使用原版本或显式迁移；默认值变化可能要求重新判定授权。迁移要记录输入、结果和副作用去重关系，无法证明兼容时保留旧环境或明确终止。

**面试官核验提示**

磁盘状态恢复成功但事件日志已经提交了后续步骤，如何发现不一致？关注恢复握手和检查点对应的事件位置。

**核验证据**

展示一次 schema 可解析但语义不兼容的迁移测试。

## 如何判断是否精通

每题沿用统一题库的 0–4 分，不增加一套总分：

| 分数 | 判断依据 |
| --- | --- |
| 0 | 核心机制错误，澄清后仍无法建立正确解释 |
| 1 | 能说术语，不能解释行为与边界 |
| 2 | 正常流程与主要机制正确，失败处理不完整 |
| 3 | 能处理失败、解释取舍并提出可执行验证 |
| 4 | 达到 3 分，且能给出可核查证据、回答条件变化后的追问 |

建议判为“本模块已展示精通”：全部题目已覆盖、每题至少 3 分、至少两题达到 4 分，并完成下面的现场核验；关键边界经过澄清后没有遗留错误。仅口述或未覆盖全部题目，记录“已覆盖部分达标/待验证”，不推算整个模块精通。评分门槛是本课程建议，不是行业认证。

现场源码、mock、真实运行时和生产经验分别记录。真实运行时或生产能力的主张，需要相应证据；不能用一次 mock 或高口述分替代。候选人采用同层、同等深度的其他开源项目也可得分。

**课程项目核验：**Q03-01/Q03-02/Q03-04 可引用 E2B/OpenHands 的具体路径，也可指出其限制并提出自己的修复设计。

**现场核验任务：**写出创建与取消状态机，在“资源已创建但状态未保存”处注入失败并说明恢复步骤。

**本模块关键误解：**超时就盲目重建；取消受理等于副作用撤销；旧快照批准状态永远有效。
