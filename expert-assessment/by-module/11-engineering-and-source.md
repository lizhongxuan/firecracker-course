## Q11-01 · 现场源码阅读

**题目**

在给定 Firecracker 提交中，从 `InstanceStart` 找到内部动作、预启动状态检查、VM 构建和 vCPU 开始执行的位置。选择一个失败分支，追踪错误如何返回调用者。解释哪些地方是线程间消息，哪些是直接调用。

**参考答案**

以下调用链按本地 Firecracker 提交 `30471852666564d980f330d0575115eda7d5ce8e` 核对。

1. [actions.rs](../../../../src/firecracker/src/api_server/request/actions.rs) 的 `parse_put_actions` 将 `InstanceStart` 转为 `ParsedRequest::new_sync(VmmAction::StartMicroVm)`。
2. [API server](../../../../src/firecracker/src/api_server/mod.rs) 通过 channel 发送动作、写 eventfd 通知 VMM，并等待响应 channel；这是线程间通信，不是直接在 HTTP 解析栈中完成所有 VM 工作。
3. [rpc_interface.rs](../../../../src/vmm/src/rpc_interface.rs) 的预启动控制器将 `StartMicroVm` 分派到 `start_microvm`，后者直接调用 `build_and_boot_microvm`。
4. [builder.rs](../../../../src/vmm/src/builder.rs) 的 `build_microvm_for_boot` 建立资源，初始 vCPU 处于暂停状态；`build_and_boot_microvm` 随后调用 `resume_vm` 允许执行。[vcpu.rs](../../../../src/vmm/src/vstate/vcpu.rs) 的 `run_emulation` 经 `self.kvm_vcpu.fd.run()` 进入 KVM 执行。
5. 以缺少内核配置为例：builder 返回 `StartMicrovmError::MissingKernelConfig`，沿 Result 传播至 `VmmActionError::StartMicrovm`；API 侧收到 VMM 结果后用 `ParsedRequest::convert_to_response` 形成响应。状态机拒绝、构建失败与客户端未收到响应是不同层次的问题。

**深入追问**

启动请求已触发 VM 运行，但 API 连接在响应前断开，客户端能否把它当作启动失败？

**追问参考答案**

客户端只知道没有收到确定响应，需要查询实际状态或通过管理器对账。沿源码区分动作接收、VM 构建/运行、结果生成与网络响应位置；不能把 HTTP 失败直接推导为 VM 未启动。若要重试，需核对运行时状态限制与平台幂等合同。

**面试官核验提示**

为什么预启动与运行期 API 路径不同？用调用位置核对直接调用、channel/eventfd 通知，而非背一串文件。以候选人实际选定提交为准。

**核验证据**

在固定提交中找到至少三个阶段的实际代码，并说明错误在哪层可见。

**常见误区**

只定位 `main.rs`，却无法说明控制流、状态限制或错误传播。

## Q11-02 · 设备实现

**题目**

沿一次 virtio 网络或块设备请求说明描述符、客户机内存、事件通知和完成响应。假设后端 I/O 可阻塞数秒，你如何修改设计而不破坏队列内存生命周期、限流、暂停与快照语义？

**参考答案**

1. 客户机驱动把请求放入 virtio 可用队列；设备后端读取描述符链，校验地址、长度、访问方向、链结构和可访问的客户机内存范围。
2. 后端执行对应宿主 I/O，成功或失败后更新完成状态/used 队列并发出所需通知。队列状态、请求缓冲区与完成结果需要保持一致。
3. 将阻塞 I/O 放入异步队列或工作线程时，限制在途数量与内存，保存请求所有权及有效缓冲区生命周期；完成通过受控通道回到设备状态管理点，并维持限流与公平性。
4. 暂停和快照必须协调所有仍可修改客户机内存/设备状态的执行者，排空、取消或保存可恢复的在途状态。错误和超时要释放资源，不能仅增加线程池就宣称快照语义不变。

**深入追问**

设备后端改用线程池后，vCPU 已暂停但工作线程仍在写 guest 内存，此时能创建一致快照吗？

**追问参考答案**

需要把设备工作与快照纳入同一同步协议。限制新请求、跟踪在途 I/O，并在可证明的切面排空或保存可恢复状态；保持缓冲区生命周期、完成通知和队列状态一致。不能无限等待无法取消的后端，也不能直接序列化仍被修改的状态；超时应显式失败或按约定回退。

**面试官核验提示**

暂停后谁可能继续改内存，快照前在哪里排空？外部 vhost-user 后端与进程内设备有何不同？要求代码或协议级依据，不接受“加线程池就好了”。

**核验证据**

画出暂停屏障、工作线程完成和快照提交的时序，指出需要维护的不变量。

**常见误区**

认为 Rust 自动证明客户机地址、长度或设备协议合法；暂停 vCPU 就忽略所有在途 I/O。

## Q11-03 · 代理协议审计

**题目**

审计下面的伪代码。指出错误边界与修复原则，并设计 4 个本地负向测试：

```text
req = decode_json(read_until_eof(connection))
tenant = req["tenant_id"]
if tenant in enabled_tenants:
    if req["operation"] == "read_artifact":
        p = realpath(workspace + "/" + req["path"])
        if p.startswith(workspace):
            return read_all(p)
    if req["operation"] == "run_tool":
        return host_shell(req["command"], credentials=global_credentials)
```

**参考答案**

1. 输入无界：`read_until_eof` 与 JSON 解析应有帧长、累计字节、超时和并发限制；输出也应在读取过程中限额，而非全部载入后再截断。
2. 身份不可信：`tenant_id` 来自请求正文，必须改为可信会话/能力绑定，并校验该主体对实际目标对象的权限。
3. 路径与对象不安全：字符串前缀可能匹配兄弟目录；`realpath` 后再打开存在替换竞态。用目录句柄、受约束解析和已打开对象校验，并处理硬链接来源、特殊文件及大小。
4. 能力过大：guest 传入任意宿主 shell 命令并使用全局凭证。改为有限能力、参数/资源授权与受限身份；任意代码放入其应有执行边界。
5. 四类测试可分别使用：伪造主体、同名前缀兄弟路径/受控替换、超长输入输出、未授权工具参数；同时保留合法请求成功用例。修复需针对不同边界，单独转义或改成 argv 不足以完成整体修复。

**深入追问**

修复已经增加路径前缀校验，如何设计测试证明它没有只覆盖正常路径？

**追问参考答案**

至少覆盖可信主体校验、同名前缀兄弟路径、校验后替换/链接、特殊文件与大小上限、操作参数及预算。测试既有允许也有拒绝，并在受控目录中制造条件变化。依据授权对象与打开后对象的不变量判断结果，不用与实现相同的字符串拼接逻辑充当唯一测试判据。

**面试官核验提示**

至少四类本地测试应覆盖身份伪造、路径/对象约束、输入/输出预算、操作参数/权限。加分项是重复 request ID 绑定参数、撤权后调用、race 测试和失败日志脱敏。不能只列漏洞名字，要解释可信端修复在哪里。

**核验证据**

现场写出四个具体输入、预期结果和各自检验的边界。

**常见误区**

只加转义、补一个 `/` 或改成 argv 就认定整体安全。

## Q11-04 · 验证安全修复

**题目**

某个修复给 virtio 描述符长度增加了检查，单测通过。你还需要什么证据才愿意发布？请区分功能测试、边界/性质测试、fuzz、性能回归和代码审计，并说明版本升级及回滚的限制。

**参考答案**

1. 确认长度与地址运算的溢出、边界、描述符链与循环/数量限制、访问权限和生命周期不变量，选取与改动风险相称的性质测试、fuzz 语料、集成和性能回归。
2. 正常用例通过不能证明不可信输入安全。

**深入追问**

长度检查通过，但地址加长度发生整数溢出或描述符链成环，测试应怎样扩展？

**追问参考答案**

验证整个地址区间计算和访问权限，使用受检查算术或等价范围证明；同时限制链长度、循环遍历和资源消耗。覆盖零长度、边界、溢出、跨区间、非法后继与错误恢复，结合性质测试和 fuzz，再检查相邻路径是否有同类问题。验证方法要对应实际风险。

**面试官核验提示**

解释测试覆盖什么、不覆盖什么；检查相同模式的相邻路径、在途状态和错误恢复。发布时考虑配置、快照/协议兼容以及回滚不能撤销已改变的状态。

**核验证据**

说明一条“任何合法访问必须在已授权内存范围内”的性质，并设计反例和失败后的资源检查。

**常见误区**

“Rust 编译通过加一个正常单测，所以不存在安全问题”。

## Q11-05 · 并发和取消

**题目**

任选 Go 或 Rust，说明如何实现一个有界并发的 rollout worker：任务可超时/取消，输出受限，结果与错误各有状态，进程退出需要清理资源。如何验证没有 data race、goroutine/task 泄漏、未等待后台任务、重复完成或死锁？编译通过能证明哪些，不能证明哪些？如果上层通过 Python 适配 OpenHands 或 verl，deadline、取消、错误分类与事件标识怎样跨到 Go/Rust worker？

**参考答案**

1. 用有界等待队列和活跃任务配额控制准入；在创建后台任务前取得容量，超限返回明确背压或拒绝，不能让排队本身无限消耗协程和内存。
2. 每个 task/attempt 有唯一状态所有者或受同步保护的转换，规定完成与取消的提交顺序，结果终态只提交一次；迟到回调只能补充审计和清理状态。
3. 将 deadline/取消传播到后端，输出读取过程中限额；结束后等待所属后台工作并回收资源。后端不支持取消时定义有界等待和必要的进程隔离，未退出资源仍受跟踪。
4. Go 可用 context、channel/锁和 race detector；Rust 可用所有权、取消信号和后台任务等待等适用机制。锁与 await、channel 阻塞和不可取消 I/O 都要专项验证，编译或 race 检查不能证明无死锁与逻辑重复完成。
5. Python 适配协议携带身份、版本、deadline、取消和结构化结束原因；可信端校验请求，避免 Python 超时后 Go/Rust 仍无界执行。用受控交错测试完成/取消、后端失败、输出超限与关闭失败。

**深入追问**

调用取消函数后，底层阻塞操作仍不返回，如何防止 worker 被耗尽？

**追问参考答案**

取消是信号，是否能中断取决于后端。设置准入、deadline 与有界等待，使用支持取消的 API；无法可靠中断的工作可放入可终止的独立进程边界。继续占用的资源仍应计费与跟踪，迟到结果不得改写已提交终态；关闭流程需要等待或报告未完成清理。

**核验证据**

用受控阻塞后端演示取消、容量占用、迟到完成与资源回收。

**源码检查点**

检查跨语言协议的身份、版本、取消和清理语义。Python 适配是课程集成练习；限时 E04 仍只要求原定 mock worker，不能临时增加整套框架部署要求。

## Q11-06 · AI 生成代码的交付责任

**题目**

你使用 AI 辅助实现 worker 和测试，演示通过，但没有覆盖取消与完成同时发生。请说明从需求分解到代码审查、故障注入、依赖核验和发布的流程。现场如何证明自己理解关键路径，如何发现 AI 生成测试只是在重复实现中的同一个错误？

**参考答案**

1. 候选人应先定义状态不变量与失败模型，再用独立验收条件检查生成实现和测试；能够说明 AI 输出哪些部分被采纳、修改或拒绝。
2. 核验依赖/API 真实可用，避免把生成代码和按同一假设生成的测试互相当作证明。
3. 临时改变完成/取消顺序、后端延迟或输出限制，要求现场解释并验证。
4. 衡量可维护性、正确性、测试有效性和研发效率；不按提示词长度、工具品牌或代码行数给分。
5. 所有辅助方式遵守本地材料约束，不要求外发源码。

**深入追问**

AI 写出的测试随机跑一千次都通过，如何更可靠地暴露取消/完成竞态？

**追问参考答案**

用可控屏障或 mock 调度点固定关键交错：取消先到、结果先到、提交后清理失败等，验证终态唯一、已知结果保留和资源最终回收。测试判据来自事先写明的合同；可加入模型化状态检查或故意破坏实现来验证测试能失败。随机压力仍有价值，但不是唯一证据。

**核验证据**

现场改变一个顺序，展示旧实现失败、修复通过及测试为何有效。

## 如何判断是否精通

每题沿用统一题库的 0–4 分，不增加一套总分：

| 分数 | 判断依据 |
| --- | --- |
| 0 | 核心机制错误，澄清后仍无法建立正确解释 |
| 1 | 能说术语，不能解释行为与边界 |
| 2 | 正常流程与主要机制正确，失败处理不完整 |
| 3 | 能处理失败、解释取舍并提出可执行验证 |
| 4 | 达到 3 分，且能给出可核查证据、回答条件变化后的追问 |

建议判为“本模块已展示精通”：全部题目已覆盖、每题至少 3 分、至少两题达到 4 分，并完成下面的现场核验；关键边界经过澄清后没有遗留错误。仅口述或未覆盖全部题目，记录“已覆盖部分达标/待验证”，不推算整个模块精通。评分门槛是本课程建议，不是行业认证。

现场源码、mock、真实运行时和生产经验分别记录。真实运行时或生产能力的主张，需要相应证据；不能用一次 mock 或高口述分替代。候选人采用同层、同等深度的其他开源项目也可得分。

**课程项目核验：**Q11-01/Q11-05/Q11-06 结合源码、取消竞态和自己的修复说明；背出函数名或只会运行官方 demo 不足以证明研发能力。

**现场核验任务：**在固定源码提交中追一条启动/错误链；对本地 worker 制造完成与取消交错并解释修复。

**本模块关键误解：**Rust 编译通过证明协议合法；race detector 通过证明无逻辑竞态；取消信号保证阻塞操作立即退出。
